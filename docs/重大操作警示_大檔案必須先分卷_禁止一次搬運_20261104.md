# 2218跨專案強制操作警示｜2026-11-04：大型檔案禁止一次性搬移

> **適用範圍：本2218帳號所有專案、所有分支；健康接班模組先讀。這是安全與工作保存規則，並非本分支已完成任何大型資料整合作業的聲明。**

## 事故與結論

- 2026-11-03～04 台股資料蒐集工作坊B線V7A在遷移GitHub已存大檔與Library大型V3 SQLite時，Linux/Python工具連續發生 \`ClientError\`，對話容器無法恢復。Owner已多次遇過相同事故，明令全部模組記錄。
- 即使已把GitHub父ZIP **726,764,752 bytes** 分成 **280MB/280MB/166.8MB** 三個Action Artifacts，並成功傳回聊天暫存，仍不足以保證Linux/Python可操作；**不要把GitHub單次可下載上限誤當健康模組容器安全上限**。
- **禁止直接在聊天／Python容器一次搬、一次解壓、一次載入或同時持有1GB級來源庫、多個數百MB ZIP、完整大型SQLite。** 不把大量bytes編入聊天或一次工具輸出。

## 後續模組必須採用的防崩潰程序

1. 原檔優先留在GitHub Release／官方原始庫／GPT Library，不要因為一次搬不動就重抓或重建。
2. 優先由獨立GitHub Actions Runner或其他資源充足的執行環境，對大檔在來源端作**差分、查缺、切片、壓縮及校驗**，只把研究實際需要的小增量傳回。
3. 若必須把完整檔案搬回，**先在來源端分小卷**，每卷建議**≤32MiB（33,554,432 bytes）**，必要時降至16MiB或更小；一卷接收→串流落地→驗尺寸與SHA256→釋放記憶體→再接下一卷。**絕對不在同一回合一次傳回所有分卷**。
4. 完整重組需在有足夠剩餘磁碟、RSS與CPU資源之隔離環境，以串流實作；按分卷順序重組，驗整檔 SHA256、壓縮包完整性、SQLite \`quick_check\`。出錯直接停止，不要在同一受損容器反覆重試。
5. 操作前先比對正式主庫已擁有資料、只補真正的缺口；不要因為搬運失敗擴大成重抓年度原件或把歷史完整庫重複上傳。
6. **已搬回聊天／容器的\`/mnt/data\`暫存不等於已持久化到Library或GitHub。** 每次交接保留權威原件URL、分卷ID、每卷SHA、完整父SHA、到期時間及「尚未真正合併」狀態。
7. 若健康容器仍不能安全搬小卷，應在隔離Runner內完成SQL核對／差分／真實驗收，只將小報告與小增量回傳；**禁止硬搬**。
